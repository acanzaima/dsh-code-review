# Host–Client 协议

本文定义 `dsh-code-review` 两半之间的通信：浏览器端的 `client.js` 如何调用 Host 半，Host 如何解析仓库、校验参数并返回数据。它是这个包唯一的内部接口，也是维护者改动 Host 方法、客户端 RPC 和测试时需要对齐的权威文档。

**谁在说话**：DSH Web 页面里的 `client.js`（`src/client/rpc.js`）向 Host Cordis 插件注册的一条 `POST /api/code-review` Fetch 路由发送 `{ method, params }`，Host 返回 `{ ok, value }` 或 `{ ok, error }`。

**为什么按包版本演进**：两半永远随同一个 npm 包一起发布，协议没有独立的版本协商，包版本就是协议版本。任何不兼容的协议变更都必须与代码、本文档和测试在同一次改动中发布；Host 与 Client 不保证跨版本兼容。

`docs/` 与 `assets/` 不进入 npm tarball：`docs/`（维护者 / 集成者文档）与 `assets/`（README 简介图）随 GitHub 仓库发布。

## 2. 客户端 bundle 格式

`client.js` 由 `scripts/build.mjs` 生成，格式固定：

```js
/* Generated by scripts/build.mjs from src/client/*.js — do not edit by hand. */
window.__ModuleLoader__.load({
  id: 'dsh-code-review',
  factory(require) {
    const React = require('react');
    const __mods = Object.create(null);
    function __def(name, fn) {
      __mods[name] = { fn: fn, exports: null };
    }
    function __req(name) {
      const mod = __mods[name];
      if (!mod) throw new Error('dsh-code-review client: unknown module ' + name);
      if (!mod.exports) {
        mod.exports = {};
        mod.fn(mod.exports, __req, React);
      }
      return mod.exports;
    }
    // 以下按固定顺序拼接 src/client/*.js 的源码，每段前有来源注释。
    return __req('app');
  },
});
```

`id` 必须与 `package.json` 的 `name` 一致；工厂函数的返回值是插件的客户端 API：`{ apply(ctx), inject: ['slots'] }`。每个源码文件是一个普通脚本：

```js
__def('diff', function (exports, require, React) {
  'use strict';
  // ...实现...
  exports.buildSideBySide = buildSideBySide;
});
```

每个客户端源码文件必须满足：

- 以 `__def('<文件名>', function (exports, require, React) { ... })` 包裹；名字与文件名一致。
- 纯脚本：无 `import` / `export`、无 JSX、无顶层 `await`。
- 同级模块只能通过 `require('模块名')` 引用，且模块名必须是构建顺序中的名字或 `'react'`。
- 不写 `document.body`；只在自己的插槽组件树内渲染。注册 `window` / `document` 级监听（键盘、可见性、焦点）时必须成对移除。
- 样式只使用 DSH 主题 CSS 自定义属性（`--dsw-*` 等 token，包括 `--dsw-shadow-lv*` 阴影令牌）；字面颜色被禁止，透明度与混色用 `color-mix()` 从 token 派生。
- 所有可见字符串同时存在于 `src/client/i18n.js` 的 zh 与 en 字典中。

构建顺序（`scripts/build.mjs` 的 `ORDER`，`app` 必须最后）：

```text
util -> i18n -> state -> rpc -> open-in-app -> diff -> diff-view -> styles -> ui -> components -> app
```

`styles` 是独立的样式表模块，由 `components.js` 的 `Styles` 组件渲染为 `<style>`；`app` 是唯一注册插槽的模块，也是工厂的返回模块。

构建是确定性的：源码按 `ORDER` 读取，行尾归一化为 LF，保证单个结尾换行，因此同一份源码重复构建字节一致。`client.js` 必须提交进仓库，`validate` 的 `client-build` 门禁会逐字节检查它是否过期。

## 3. 传输

Host 在 Cordis 插件中注册一条精确路径的 Fetch 路由：

```js
ctx.inject(['connection'], (connectionCtx) => {
  connectionCtx.effect(
    () =>
      connectionCtx.connection.fetch.register({
        path: '/api/code-review',
        methods: ['POST'],
        requestBody: 'buffered',
        fetch: (request) => plugin.route(request),
      }),
    'code-review: /api/code-review Fetch route',
  );
});
```

DSH 的 Connection 层负责认证浏览器会话，只转发认证通过的请求；插件不读取、不保存令牌。

请求体：`{ "method": string, "params": object }`。

响应体：

```ts
type Envelope<T> =
  | { ok: true; value: T }
  | { ok: false; error: { code: string; message: string; details?: object } };
```

HTTP 状态约定：

- 正常的协议回复均为 `200`，包括 `{ ok: false }` 的业务错误。
- 只有传输层问题才返回非 200：非 `POST` 返回 `405`，请求体不是 JSON 返回 `400`。
- 客户端把任何非 2xx 响应视为传输错误（`transport/http-<status>`），并区分 `transport/bad-json`（响应不是 JSON）与 `transport/bad-envelope`（响应不是对象）。

**仓库解析**：需要仓库的方法按 `sessionId` → 显式 `cwd` → 插件默认 cwd（`ctx.workingDirectory.defaultDirectory`，缺失时退回进程 cwd）解析。需要仓库的方法在解析失败时抛出 `repo/no-git` 等协议错误；`status` 是例外，它返回 `state: "no-git"` / `"error"` 的空状态，便于窗口显示空态。`settingsGet` / `settingsSet` / `models` / `classifyCancel` 不解析仓库。

除 `classifyCancel` 外，所有会接触仓库的方法在回复里都带 `repo`；客户端据此判断回复是否属于当前仓库，并丢弃迟到的其它仓库响应。

## 4. 方法

| method | params | value |
| --- | --- | --- |
| `status` | `{ sessionId?: string, cwd?: string }` | `StatusPayload` |
| `diff` | `{ sessionId?, cwd?, key: string }` | `EntryDiff` |
| `stage` | `{ sessionId?, cwd?, keys: string[] \| "all", includeUntracked?: boolean, expected: ExpectedFingerprints }` | `OpResult` |
| `unstage` | `{ sessionId?, cwd?, keys: string[] \| "all", expected: ExpectedFingerprints }` | `OpResult` |
| `discard` | `{ sessionId?, cwd?, key: string, expected: Fingerprint }` | `OpResult` |
| `stageHunk` | `{ sessionId?, cwd?, key: string, hunkIndex: number, expected: Fingerprint }` | `OpResult` |
| `unstageHunk` | `{ sessionId?, cwd?, key: string, hunkIndex: number, expected: Fingerprint }` | `OpResult` |
| `discardHunk` | `{ sessionId?, cwd?, key: string, hunkIndex: number, expected: Fingerprint }` | `OpResult` |
| `commit` | `{ sessionId?, cwd?, message: string, expected: CommitExpectation }` | `CommitResult` |
| `pushPreview` | `{ sessionId?, cwd?, remote?: string, targetBranch?: string }` | `PushPreview` |
| `push` | `{ sessionId?, cwd?, remote?: string, targetBranch?: string, setUpstream?: boolean }` | `PushResult` |
| `remoteSet` | `{ sessionId?, cwd?, name: string, url: string }` | `RemoteSetResult` |
| `classify` | `{ sessionId?, cwd?, requestId: string, entries?: Array<{ key: string }>, force?: boolean }` | `ClassifyResult` |
| `classifyCancel` | `{ requestId: string }` | `{ cancelled: boolean }` |
| `models` | `{ sessionId? }` | `ModelCatalog` |
| `settingsGet` | `{ sessionId? }` | `SettingsValue` |
| `settingsSet` | `{ sessionId?, patch: object }` | `SettingsValue` |

所有写方法（`stage` / `unstage` / `discard`、三个 hunk 方法、`commit`、`push`、`remoteSet`、`settingsSet`）共享插件级写链，串行执行；其中接触仓库的写方法（含 `remoteSet`）返回的 `status` 都是写后重新读取的 `StatusPayload`，`settingsSet` 返回最新的 `SettingsValue`。

参数细节：

- `keys` 为字符串数组或 `"all"`；数组最多 5000 个键，每个键必须是非空字符串。
- `includeUntracked` 默认 `true`；仅对 `keys: "all"` 有意义，数组形式按显式键处理。
- `stage` / `unstage` 必须携带 `expected`：`Record<entryKey, Fingerprint>`，值为客户端最后一次从 `status` 看到的该条目 `fingerprint` 原样对象。Host 先重新读取状态，再校验目标集合：
  - 数组形式的目标集合就是 `keys`；`"all"` 的目标集合是**完整仓库**范围（不受 2000 行展示上限影响）：`stage` 为全部 unstaged 行加 untracked 行（冲突行跳过并列入 `skipped`，已暂存行不是目标）；`unstage` 为全部 staged 行。
  - 每个目标 key 必须存在于当前状态，且其最新指纹必须与 `expected[key]` 的全部字段（`base` / `target` / `mode` / `gitlink`）一致；`"all"` 时 `expected` 的 key 集合必须与目标集合完全相等（多一个或少一个都拒绝）。
  - 任一不满足返回 `entry/stale`，不执行任何写入；缺少或非法的 `expected` 同样按 `entry/stale` 处理。
- `stage` 的数组形式会把冲突条目显式暂存（标记为已解决）；`stage "all"` 不会自动处理冲突条目。
- `hunkIndex` 必须是非负整数，且指向该文件当前 diff 中的 hunk；hunk 写操作的 `expected` 来自**当前展示的 diff** 的 `entry.fingerprint`。
- `commit` 的 `expected` 为 `{ headSha, stagedFingerprint }`；`stagedFingerprint` 来自最近一次 `status`，覆盖完整暂存区。
- `pushPreview` 与 `push` 的 `remote` / `targetBranch` 是可选的；`push` 的源分支永远取 Host 当前本地分支，客户端不能指定。`push` 未设置上游且未指定 `setUpstream: true` 时返回 `push/upstream-missing`。
- `remoteSet` 的 `name` 必须匹配 `^[A-Za-z0-9][A-Za-z0-9._-]*$` 且不超过 200 字符；`url` 会先 `trim`，必须非空、不超过 2048 字符、不含控制字符且不以 `-` 开头（避免被当作 git 选项）。URL **只做语法校验**：Host 只写本地 Git 配置（同名远程用 `git remote set-url` 更新地址，不存在则 `git remote add`），不检查地址可达性、不发起网络请求，错误的地址或凭据由后续 push / fetch 的 Git 报错暴露。
- `classify` 的 `entries` 只信任 `key`：Host 重新读取状态并用真实条目构造分类输入；提供的 key 不在当前状态中返回 `entry/not-found`，省略 `entries` 时归类当前状态的全部条目。
- `classify` 的 `requestId` 用于取消和标识结果；同一 `requestId` 的新请求会中止旧请求，`classifyCancel` 可按 id 取消。
- `settingsSet` 的 `patch` 支持 `aiClassify`（boolean）、`preclassify`（boolean，会话空闲时预归类）、`maxCandidates`（number）、`locale`（`"zh"` / `"en"` / `null`）、`customInstructions`（≤ 4000 字符的字符串 / `null`）、`provider` / `model`（字符串 / `null`，必须成对设置或清除）、`reasoningEffort`（≤ 64 字符的字符串 / `null`，属于当前模型的推理档位）。`null` 表示清除该字段。修改 `provider` / `model` 且未携带新的 `reasoningEffort` 时，Host 会清除旧档位，避免把 A 模型的档位应用到 B 模型。

## 5. 数据形状

```ts
type RepoRef = {
  root: string;                // 仓库根目录绝对路径（Windows 使用原生分隔符）
  gitDir: string;              // git rev-parse --absolute-git-dir（worktree 也正确）
  branch: string | null;       // 短分支名；detached 时为 null
  detached: boolean;
  headSha: string | null;      // 仓库还没有第一个提交时为 null
  upstream: string | null;     // 例如 "origin/main"
  ahead: number;
  behind: number;
  remotes: { name: string; url: string }[];
  worktree: boolean;
};

type EntryStatus = 'staged' | 'unstaged' | 'untracked' | 'conflict';
type EntryChange = 'added' | 'modified' | 'deleted' | 'renamed' | 'copied' | 'typechange' | 'conflict';
type EntryKind = 'text' | 'binary' | 'symlink' | 'submodule' | 'empty' | 'conflict';

type Entry = {
  key: string;                 // 稳定 id，见第 6 节
  status: EntryStatus;
  change: EntryChange;
  path: string;                // 当前路径；删除条目为旧路径
  oldPath: string | null;      // 重命名 / 复制的源路径
  kind: EntryKind;
  isUntracked: boolean;
  hasBothSides: boolean;       // 同一路径同时出现在 staged 与 unstaged 列表中
  additions: number;           // 非文本条目为 0
  deletions: number;
  fingerprint: Fingerprint;    // 该条目的内容 + 身份指纹（客户端视为 opaque）
  submodule?: { oldSha: string | null; newSha: string | null } | null;
  symlink?: { target: string | null } | null;
};

type Fingerprint = {
  base: string;                // 该侧不存在为 "empty"；子模块目录侧为 "dir"；
                               // git 对象侧为 git object id（十六进制）；工作区文件侧为内容 SHA-256
  target: string;
  mode?: string;               // 仅 tracked 行：如 "100644:100755"（staged=HEAD→index，unstaged=index→worktree）
  gitlink?: {                  // 仅子模块行：gitlink 两侧的提交 SHA（未知为 null）
    oldSha: string | null;
    newSha: string | null;
  };
};

/** stage / unstage 的预期指纹集合：entryKey -> 客户端最后一次看到的 fingerprint。 */
type ExpectedFingerprints = Record<string, Fingerprint>;

type StatusPayload = {
  repo: RepoRef | null;
  cwd: string;
  state: 'ok' | 'no-git' | 'error';
  error?: { code: string; message: string };
  gitVersion?: string | null;
  entries: Entry[];
  summary: {
    files: number;                 // 去重后的路径数
    entries: number;               // 列表行数（同一文件可能同时有 staged 与 unstaged 行）
    staged: number;
    unstaged: number;
    untracked: number;
    conflicts: number;
    stagedAdditions: number;       // 仅 staged 范围：HEAD → 暂存区
    stagedDeletions: number;
    unstagedAdditions: number;     // 仅 unstaged 范围：暂存区 → 工作区
    unstagedDeletions: number;
    untrackedFiles: number;        // 未跟踪文件不计入任何行数统计
    truncated: boolean;            // 条目列表本身被截断
  };
  stagedFingerprint: string;       // 完整暂存区的规范指纹，提交时回传；不受 2000 行展示上限影响
  generatedAt: number;             // 毫秒时间戳
};

type DiffSide = {
  label: string;              // 'HEAD' | 'Index' | 'Worktree' | 'Untracked' | 'Empty' | 'Index (ours)'
  ref: string;                // 例如 'HEAD:f.txt'、':0:f.txt'、'worktree:f.txt'、'empty'
  exists: boolean;
  binary: boolean;
  tooLarge: boolean;
  truncated: boolean;
  encoding: 'utf8' | 'binary';
  bytes: number;
  lines: number;              // 实际返回的行数
  text: string;               // 完整文本；binary / tooLarge 时为空；truncated 时为截断后的文本
};

type Hunk = {
  index: number;
  header: string;             // git 的 '@@ -a,b +c,d @@ ...'
  oldStart: number; oldLines: number;
  newStart: number; newLines: number;
  section: string;            // 第二个 '@@' 之后的文本
  lines: { kind: '+' | '-' | ' '; text: string; oldLine: number; newLine: number }[];
  patch: string;              // 该单个 hunk 的完整补丁文本（含文件头）
};

type EntryDiff = {
  repo: RepoRef;
  entry: Entry;
  comparison: {               // 比较基准的人类可读说明
    baseLabel: string;        // 例如 'HEAD'、'Index'、'Empty'
    targetLabel: string;      // 例如 'Index'、'Worktree'、'Untracked'
    baseRef: string;
    targetRef: string;
  };
  base: DiffSide;
  target: DiffSide;
  hunks: Hunk[];
  stats: { additions: number; deletions: number };
  unsupported?: {
    code: 'conflict' | 'binary' | 'submodule' | 'symlink' | 'too-large' | 'mode-only';
    message: string;
  } | null;
  modeChange?: { oldMode: string; newMode: string } | null;
};

type OpResult = {
  repo: RepoRef;
  ok: true;
  affected: string[];          // 受影响的路径
  skipped?: string[];          // stage "all" 时被跳过的冲突条目键
  kind?: 'stage' | 'unstage' | 'discard'; // 仅 hunk 方法返回
  status: StatusPayload;       // 写后重新读取
};

type CommitExpectation = { headSha: string | null; stagedFingerprint: string };

type CommitResult = {
  repo: RepoRef;
  headSha: string;             // 新提交的完整 SHA
  shortSha: string;
  summary: string;             // 提交信息第一行
  status: StatusPayload;       // 刷新后的状态
};

type PushPreview = {
  repo: RepoRef;
  branch: string | null;         // 兼容字段，等于 sourceBranch
  sourceBranch: string | null;   // 当前本地分支（推送源，只读）
  targetBranch: string | null;   // 目标分支（请求值 → 同远程的 upstream → 源分支）
  remote: string | null;         // 实际选中的远程
  remotes: { name: string; url: string }[];
  upstream: { remote: string; branch: string; ref: string } | null;
  defaultRemote: string | null;  // 有 origin 时为 origin，否则第一个远程
  commits: { sha: string; shortSha: string; subject: string }[]; // 将要推送的提交
  commitsBase: string | null;    // 比较基准（refs/remotes/<remote>/<target> 或 null=首推）
  canPush: boolean;
  reason?: string;               // 不能推送的原因（detached HEAD / no remotes / unknown remote / ...）
};

type PushResult = {
  repo: RepoRef;
  ok: true;
  remote: string;
  branch: string;                // 兼容字段，等于 sourceBranch
  sourceBranch: string;
  targetBranch: string;
  setUpstream: boolean;
  stdout: string;
  stderr: string;
  status: StatusPayload;
};

type RemoteSetResult = {
  repo: RepoRef;
  ok: true;
  name: string;                // 远程名称（如 "origin"）
  url: string;                 // 保存后的地址（客户端 trim 后的值）
  created: boolean;            // true=新增远程；false=已有同名远程、地址被更新
  status: StatusPayload;       // 写后重新读取
};

type ClassifyKey = { key: string }; // classify 请求只携带 key；元数据由 Host 从 status 重建

type ClassifyResult = {
```

| 项 | 上限 | 行为 |

| 错误 details 中的 stderr | 16 KiB | 超出截断 |

## 6. Entry key 与指纹

Entry key 是客户端与服务端之间引用条目的稳定 id：

```text
<status>:<path>                  # staged、unstaged、untracked、conflict
staged:<oldPath>:<path>          # staged 的重命名 / 复制条目（path 为新路径）
```

示例：

- `staged:src/app.js`
- `unstaged:src/app.js`
- `staged:src/old.js:src/new.js`
- `untracked:docs/new.md`
- `conflict:src/app.js`

客户端只回传 key 与 `expected` 指纹，不传路径。Host 在每个请求开始时重新读取状态，用 key 在当前列表中定位条目；key 不存在返回 `entry/not-found`。

`Entry.fingerprint` 的语义（客户端不解释、只原样回传）：

- `base` / `target` 是两侧的身份：该侧不存在为 `"empty"`；子模块目录侧为 `"dir"`；**git 对象侧为 git object id**（内容寻址，状态轮询因此不需要读取大 blob）；工作区文件侧为内容 SHA-256（大文件流式计算）。
- `mode` 只在 tracked 行出现，记录该条目的 mode 对（例如 `"100644:100755"`）；`gitlink` 只在子模块行出现，记录 gitlink 两侧的提交 SHA。
- 因此**不能假设指纹总是 64 位十六进制**；客户端只把它当 opaque 值。

写操作前 Host 重新计算指纹，并按上述全部字段与 `expected` 比较；任何字段不一致返回 `entry/stale`，不执行任何写入。`stage` / `unstage` 的集合语义见第 4 节：`"all"` 要求 `expected` 的 key 集合与完整仓库目标集合完全相等。

`stagedFingerprint` 不是由展示条目拼出来的：它由完整 index 的 `git ls-files -s -z` 记录（path、mode、oid、stage）规范化后计算 SHA-256，空 index 为 `""`。因此展示列表被截断（或隐藏了任何暂存条目）时，提交前的 `commit/stale` 校验仍然覆盖完整暂存区。`mode` / submodule gitlink 的变化也天然包含在这个指纹与条目指纹里。

## 7. 错误码

协议错误始终通过 `{ ok: false, error }` 返回。`message` 是**稳定的英文诊断**（不含用户输入、异常原文、路径或堆栈）；用户可见文案由客户端按 `error.code` 本地化为中文 / 英文。`details` 是可选诊断数据，只含安全字段（key、expected/actual、argv、exitCode、裁剪后的 stdout/stderr、hookOutput 等）。错误码按区域分组：

| 错误码 | 含义 |
| --- | --- |
| `repo/not-found` | 指定的 cwd 不存在或不可访问 |
| `repo/no-git` | 目录不是 Git 仓库 |
| `repo/git-unavailable` | 无法执行 `git` 命令 |
| `repo/locked` | 仓库被锁（例如 `index.lock`） |
| `repo/error` | 仓库解析的其他失败（作为 `status` 空状态中的 `error` 返回） |
| `repo/timeout` | 单次 git 调用超过 120 秒 |
| `repo/output-too-large` | 单次 git 调用的 stdout+stderr 超过 64 MiB |
| `entry/not-found` | 条目 key 不在当前状态中 |
| `entry/unsupported` | 该条目类型不支持此操作（hunk 操作、discard 等） |
| `entry/conflict` | 条目处于未解决冲突状态 |
| `entry/stale` | 指纹与客户端预期不一致 |
| `patch/mismatch` | hunk 身份在写入前发生变化，补丁无法精确应用 |
| `commit/empty-index` | 暂存区为空 |
| `commit/invalid-message` | 提交信息为空 |
| `commit/conflict-pending` | 存在未解决冲突，禁止提交 |
| `commit/stale` | HEAD 或暂存区内容在预览后变化 |
| `commit/failed` | `git commit` 失败（钩子、签名等） |
| `push/no-remote` | 没有可用远程，或指定的远程不存在 |
| `push/no-branch` | detached HEAD，无法推送分支 |
| `push/upstream-missing` | 分支没有上游且未请求设置上游 |
| `push/rejected` | 远端拒绝（通常是非快进，需要先拉取合并） |
| `push/auth` | 认证 / 权限失败 |
| `push/network` | 网络或主机不可达 |
| `remote/invalid` | `remoteSet` 的名称或地址不合法（名称不匹配规则 / 超长；地址为空、超长、含控制字符或以 `-` 开头） |
| `remote/failed` | `git remote add` / `git remote set-url` 执行失败（`details` 带 argv 与裁剪后的 stderr） |
| `settings/invalid` | 设置 patch 不合法 |
| `ai/disabled` | AI 归类已在设置中关闭 |
| `ai/unavailable` | 没有可用的 `llm` 服务或可解析的模型路由，或模型请求失败（`details.reason` 携带稳定失败码，如 `NO_ADAPTER`、`AUTH`、`RATE_LIMIT`） |
| `ai/invalid` | 模型回复不是约定的 JSON 结构，或没有任何可用分类 |
| `ai/aborted` | 归类请求被取消或超时中止 |
| `internal` | 未预期错误或参数形状错误（未预期异常固定返回 `Internal error`，原文只进日志） |
| `protocol/unknown-method` | Host 不认识请求的方法：常见于客户端 bundle 已更新但 Host 半未重启（两端版本不一致），重启 DSH 后重试 |

客户端另有三个传输层错误码：`transport/http-<status>`、`transport/bad-json`、`transport/bad-envelope`。客户端必须为上述每个 code 提供 zh/en 文案；未知 code 回退到本地化的通用错误文案。

## 8. Git 引擎语义

`src/host/git.js` 是 ESM 纯 Node 模块，不导入 DSH，不调用 `process.chdir`，不经过 shell，所有调用都是 argv 数组。

```text
export function createGit(exec)
// Executor: {
//   run(argv: string[], opts?: { cwd?: string, env?: object, input?: string | Buffer, literal?: boolean }):
//     Promise<{ code: number, stdout: Buffer, stderr: Buffer }>
// }
// 所有 Git 调用都满足 argv[0] === 'git'。

const git = createGit(exec);

git.resolveRepo(cwd)                              // -> Promise<RepoRef>，失败抛 GitError
git.status(repo, { maxEntries?: number })          // -> Promise<StatusPayload>；Infinity = 完整列表（内部用于全局写操作）
git.diff(repo, key, { status })                   // -> Promise<EntryDiff>
git.stage(repo, { keys, includeUntracked, expected, status })    // -> Promise<{ affected, skipped? }>
git.unstage(repo, { keys, expected, status })     // -> Promise<{ affected }>
git.discard(repo, { key, expected, status })      // -> Promise<{ affected }>
git.stageHunk(repo, { key, hunkIndex, expected, status })
git.unstageHunk(repo, { key, hunkIndex, expected, status })
git.discardHunk(repo, { key, hunkIndex, expected, status })
git.commit(repo, { message, expected, status })   // -> Promise<CommitResult>
git.pushPreview(repo, { remote, targetBranch, status })       // -> Promise<PushPreview>
git.push(repo, { remote, targetBranch, setUpstream, status }) // -> Promise<PushResult>；源分支由 Host 决定
git.setRemote(repo, { name, url })                            // -> Promise<{ name, url, created }>；只写本地配置，不联网
git.gitVersion()                                  // -> Promise<string>

export class GitError extends Error { code; details; }
export function createNodeExecutor(options?: {
  gitPath?: string, logger?: object,
  timeoutMs?: number,        // 默认 120_000；超时 reject（err.code === 'timeout'）
  maxOutputBytes?: number,   // 默认 64 MiB；超限 reject（err.code === 'output-too-large'）
})
export function computeIndexFingerprint(lsFilesZOutput)  // 完整 index -> stagedFingerprint
export function fingerprintEquals(expected, actual)      // base/target/mode/gitlink 全字段比较
```

语义约束（不可随意放宽）：

- 已暂存 diff 的基准是 `HEAD`（`git cat-file -p HEAD:<path>`，无 HEAD 时为空），目标是暂存区 blob（`git show :<path>`）；未暂存 diff 的基准是暂存区 blob，目标是工作区字节；未跟踪 diff 的基准为空，目标是工作区字节；删除条目的目标为空。
- 重命名 / 复制经 `git status --porcelain=v2 -z` 识别；staged 重命名用 `-M` 针对旧路径生成 diff。
- 每个操作都返回从 Git 重新读取的数据；不存在跨请求的仓库状态缓存。
- `expected` 指纹在任何写入之前重新校验；集合类写操作（`stage` / `unstage`）要求 `expected` 覆盖目标集合，缺失或不一致抛 `entry/stale`，不写入。
- hunk 操作：用原始 diff 行重新生成只含该 hunk 的补丁（含精确文件头）；写入前重新读取状态、校验 entry 指纹，并确认 `hunkIndex` 仍落在该文件的当前 diff 中，然后 `git apply --cached`（暂存）/ `git apply --cached -R`（取消暂存）/ `git apply -R`（还原工作区）。
- `git commit` 的提交信息通过 stdin 传入（`git commit -F -`），绝不作为 argv 值；钩子与签名保持启用。提交前校验 HEAD、**完整 index 指纹**、无冲突、暂存区非空。
- `git push` 永不使用 force；源分支始终取当前本地分支，显式 refspec 为 `refs/heads/<source>:refs/heads/<target>`，`setUpstream` 时加 `-u`；设置 `GIT_TERMINAL_PROMPT=0` 避免交互式卡住。预览的“待推送提交”只用 `refs/remotes/<remote>/<target>` 作为比较基准，从不使用本地分支，也不执行 fetch。
- `git remote add` / `git remote set-url` 只写本地 Git 配置，**不访问网络**：地址不可达或凭据错误不会在 `remoteSet` 阶段报错，要等后续 push / fetch 时由 Git 报告；已存在同名 remote 时更新地址，否则新增，返回值用 `created` 区分。
- 每次 git 调用受 120 秒超时与 64 MiB 输出上限约束（`repo/timeout` / `repo/output-too-large`）；按路径传递的参数一律配合 `GIT_LITERAL_PATHSPECS=1`（Executor 的 `literal` 选项），文件名不会被解释为 glob / pathspec magic。
- 状态阶段只读取 git 对象的大小与身份，不读 blob 正文（对象侧指纹 = object id）；`diff` 先判大小再决定是否加载正文，超大对象直接标记 `too-large`。工作区大文件用流式哈希，不整体读入内存。
- 二进制、符号链接、子模块、仅模式变化、冲突与超限（`too-large`）条目的 diff 被标注为 `unsupported`；hunk 操作与 `discard` 对不支持的类型抛 `entry/unsupported`，不会静默退化成整文件操作。重命名 / 复制条目也不支持 hunk 操作，需整文件暂存。
- 被截断（`truncated`）的 diff 侧会带截断标记，界面提示当前只展示补丁范围；`hasFullContext` 为 `false`。
- 没有第一个提交的仓库（`headSha === null`）必须支持状态、diff、stage / unstage / hunk 操作与提交。

## 9. 客户端 diff 模型

`src/client/diff.js` 是纯 JS 模块：无 React、无 DOM，可以在 Node 中通过伪造的 `__def` 直接求值并测试。

```text
exports.buildSideBySide(entryDiff)                    // -> SideBySide
exports.changeAnchors(sideBySide, renderedRows)       // -> { index, top, height, hunkIndex }[]
exports.defaultExpanded(sideBySide, contextLines = 3) // -> boolean[]，每个折叠区一项
exports.detectLanguage(path)                          // -> string | null
exports.highlight(text, language)                     // -> { line, spans: [{ text, cls }] }[]
exports.findNextChange(sideBySide, fromIndex, direction) // -> number
exports.buildRows(sideBySide, expanded, contextLines) // -> Row[]，供渲染器消费
exports.highlightLine(text, language)                 // -> spans，供单行高亮复用
exports.rowCount(rows)                                // -> number
exports.rowIndexToOriginal(rows, renderedIndex)       // -> number，渲染行 → 模型行
exports.findNextChangeInRows(rows, fromIndex, direction)
```

模型：

```ts
type SideLine = { no: number | null; text: string; kind: 'ctx' | 'add' | 'del' | 'empty' };
type SideRow = {
  left: SideLine;
  right: SideLine;
  change: boolean;
  hunkIndex: number | null;
  gapStart?: boolean;
  gapEnd?: boolean;
};
type SideBySide = {
  rows: SideRow[];
  changeRowIndexes: number[];   // 变更行的渲染索引（升序）
  hunkRowRanges: { index: number; start: number; end: number }[];
  hasFullContext: boolean;      // 任一侧被截断 / 不支持时为 false
  language: string | null;
  stats: { additions: number; deletions: number };
  // 渲染辅助字段，由 DiffPane 使用：rowCount、gaps、changeBlocks、
  // truncatedSides、unsupported、modeChange。
};
```

`buildRows()` 返回的数组上还挂有 `rowCount`、`rowIndexToOriginal`（渲染行 → 模型行，合成行为 `-1`）、`changeRowIndexes`（渲染索引）与 `gapIndexes`；合成行带有 `kind: 'gap'` 或 `truncationRow: true` 标记。

要求：

- 用 Host 提供的 `hunks` 放置变更与上下文，同时用 `base.text` / `target.text` 展示 git ±3 行上下文之外的未变更内容。
- 变更行必须成对对齐：删除行在左、对应新增行在右；上下文行两侧同时是 `ctx`，空位一侧为 `empty`。
- 未变更区域按折叠区分块，`buildRows(sideBySide, expanded)` 负责展开 / 收起；每行保留 `hunkIndex`，折叠不改变 hunk 映射。
- `changeRowIndexes` 驱动上一处 / 下一处变更导航；minimap 锚点按默认展开布局计算，每个变更块一个锚点且单调递增。
- 纯函数：同样的输入产生同样的输出，不在模型层访问 DOM 或全局状态。

`test/diff.test.mjs` 覆盖纯插入、纯删除、行数不等的替换、相邻 hunk、单行文件、空的一侧（未跟踪 / 删除）、CRLF、CJK、仅模式变化、截断标记与对齐不变量。

## 10. 协议变更检查清单

修改 Host 与 Client 之间的任何内容时，以下几处必须一起改：

1. `src/host/index.js`：方法表与实现；新方法放入 `methods`，写操作包进写链。
2. `src/host/protocol.js`：新的参数读取 / 规范化函数（如果引入新参数形状）。
3. `docs/protocol.md`：本文件的 method 表、数据形状、错误码与上限。
4. `src/client/app.js` 等调用点：通过 `rpc.call` 使用新方法；`src/client/rpc.js` 只在传输层变化时需要改。
5. 测试：`test/host-plugin.test.mjs` 覆盖分发与参数校验；Git 行为变化补 `test/git-core.test.mjs`；客户端产物 / 插槽变化补 `test/client-bundle.test.mjs`。
6. 客户端源码变化后运行 `npm run build`，最后跑 `npm run validate -- --with-tests`。
